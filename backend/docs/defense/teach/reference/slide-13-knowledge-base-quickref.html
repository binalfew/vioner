Two guarantees — defensive design

Guarantee 1

Validation never blocks. Flag is metadata; record persists; UI shows flag; analyst decides. The KB does not gatekeep.

Guarantee 2

Enrichment never invents. No alias match ⇒ raw surface form persists; canonical fields empty. The KB never fabricates ids.

Pre-loaded interrupts

Q · "Only 150? ACLED has thousands."
ACLED's full list mixes live + dissolved + splinter. 150 covers active landscape. Inactive ⇒ false-positive enrichments. Mean 4.2 aliases/group = canonicalisation quality. Rec. 2 §7.4 → ongoing curation.
Q · "Why both validate AND enrich?"
Different questions. Validation: is this plausible? (correctness). Enrichment: same entity as X? (canonicalisation). One resource, two distinct knowledge gaps the model alone can't close. Operational impact on slide 19.
Q · "What about the 35.7 % unmatched?"
Raw surface form persists. Canonical fields empty. No fabrication. New armed groups not yet in the KB land exactly here. Analyst sees raw text; can flag for KB curation.
Q · "Why doesn't validation block?"
Flag is metadata, not veto. Record persists; UI shows flag; analyst re-reads. Blocking on plausibility would lose records describing genuinely unusual events.
Q · "How do you keep the KB current?"
Rec. 2 §7.4 — part-time domain expert, quarterly cadence. KB is JSON loaded at startup ⇒ adding aliases / new groups = config change, not code change. Architecture makes curation cheap.

Delivery traps to avoid

  • "We couldn't curate more" ⇒ apologetic. Use active, not historical.
  • "Validation catches errors AND enrichment improves quality" ⇒ reads as one role split in two. Name the questions each answers.
  • "In future work we'd…" ⇒ deflects the scope defence. The 150 must be defended on its own merits first.
  • Don't deploy the analyst-trust / user-testing impact here — that lives on slide 19.
