Lesson 15 · Slide 13

The curated knowledge base

The KB contribution made visible. A small, deliberate lookup layer that sits on top of the trained model — one resource doing two jobs that the model alone cannot. Validate the world facts the model never saw; canonicalise the surface forms the model cannot resolve. The slide's job is to defend the scope (why only 150?) and the roles (why both validate and enrich?) in 75 seconds.
Slide: 13 of 22 Target time: 75 seconds Hero line: "Validation never blocks extraction; enrichment never invents data" Reserved cards: 150 · 200 · 54 · 38 · 4.2 aliases · 2.4 % flag · 64.3 % enrich · slide 19

1 · Where this slide sits in the arc

Slides 10–12 built the data and modelling story — the schema, the taxonomy, the corpus, the training recipe. Slide 13 introduces the external knowledge the model itself cannot acquire from text. BERT learned patterns in a corpus; it did not learn that Al-Shabaab operates in the Horn of Africa, not Eastern DRC, and it did not learn that "Al Shabaab", "al-shabaab", and "Al-Shabaab militants" all refer to the same canonical entry. The KB injects exactly those two missing pieces — world knowledge for plausibility, alias tables for canonicalisation.

The function of slide 13. Two jobs. (1) Make the KB visible as a contribution — not a footnote, not an afterthought. The KB has its own composition numbers, its own operational rates, and a defensible scope decision. (2) Set up the operational impact that slide 19 will deepen. Slide 13 introduces the rates (2.4 %, 64.3 %); slide 19 connects them to user testing and analyst behaviour. The numbers must land here so they pay off there.

3 · The "one resource, two roles" mental model

The KB is the second complementarity claim in the deck. Slide 12's was focal × class weights — two rebalancers attacking different parts of the imbalance problem. Slide 13's is validate × enrich — two roles for one curated resource, attacking different parts of the knowledge gap the model has.

The two-axes picture for the KB

Validation

Correctness axis
Is this plausible?

×
Enrichment

Canonicalisation axis
Is this the same as X?

One curated resource, two distinct knowledge gaps closed
Why each role is needed. Validation answers "is this geographically plausible?" — a truth-conditional question. The model cannot answer this from text alone; it needs a world fact (Al-Shabaab country-of-operation). Enrichment answers "is this surface variant the same entity as another?" — an identity-conditional question. The model produces correct strings but cannot collapse them to a single id without an alias table. Validation alone leaves analytics broken (duplicate actor counts). Enrichment alone leaves implausible extractions silent (false-positive events propagate into reports). The two roles attack different aspects of the knowledge gap; neither does the other's job.

4 · One worked example — Al-Shabaab

If the panel asks for a concrete walk-through, this is the single example to carry. It is the canonical KB worked example because it exercises both roles in one sentence pair.

Sentence A — successful enrichment

Surface form "Al-Shabaab militants attacked a village in southern Somalia."
Enrich ACTOR "Al-Shabaab militants" → KB canonical al_shabaab (alias match, confidence high). Country-of-operation: SO. LOCATION "southern Somalia" → SO. Validation check: match → no flag. Record persists with canonical actor id.

Sentence B — validation flag

Surface form "Al-Shabaab fighters were active near Goma in eastern DRC."
Enrich ACTOR "Al-Shabaab fighters" → KB canonical al_shabaab. Country-of-operation: SO. LOCATION "Goma" → CD (DRC).
Validate Country mismatch SO ≠ CD ⇒ geographic plausibility flag attached. Record still persists. UI shows the flag as a coloured chip prompting analyst re-read. Extraction is not dropped.
What this example does for the slide. One pair of sentences makes both roles concrete in three breaths. Sentence A shows enrichment (surface → canonical). Sentence B shows validation (canonical actor × extracted location ⇒ flag). The same canonical entry al_shabaab participates in both — that is what "one curated resource, two roles" looks like operationally. Carry this in your pocket; deploy if a panellist asks "can you give me a concrete case?"

6 · The two-guarantees defence — the core skill

The hero line is structurally important. It is not a description of what the KB does — it is a description of what the KB refuses to do. Two negative guarantees, side by side. This is the slide's central craft skill: defending an external knowledge component with constraints, not capabilities.

Guarantee 1 — Validation never blocks

The flag is metadata, not a veto. The record persists; the UI displays the flag. The analyst decides what to do. The KB does not gatekeep the extraction pipeline.

Guarantee 2 — Enrichment never invents

If the surface form does not match any KB entry, the record carries the raw text. No fabrication. The KB augments; it never substitutes for what the model actually extracted.

Why this defence works. The standing CS-panel anxiety about a curated KB is that it will distort the pipeline — block extractions the curator didn't anticipate, or hallucinate canonical entries that don't match the source. The two guarantees explicitly refuse both failure modes. By stating the constraints up front, the slide turns "what if the KB is wrong?" into a manageable question: a wrong validation flag is visible metadata an analyst can override; a missing enrichment leaves raw text the analyst can read. Neither failure mode silently corrupts the output.

7 · The complementarity defence — second use

Slide 12 introduced the complementarity claim for focal × class weights — two rebalancers, two distinct axes (across classes × across difficulty). Slide 13 deploys the same shape for validate × enrich. The three-move defence is identical; the axes are different.

The three-move complementarity defence — applied to the KB

1Name the two roles. "Validation and enrichment." Use the role names; the panel infers two functions.
2Name the two distinct axes. Correctness vs canonicalisation. Validation answers "is this plausible?" — correctness. Enrichment answers "is this the same as X?" — canonicalisation. This is the load-bearing move.
3Point to the operational evidence. "Slide 19 / §6.7 shows the operational impact on user testing." Slide 13 plants the rates (2.4 %, 64.3 %); slide 19 converts them to analyst behaviour evidence.
The trap. If asked "why both?", do not say "validation catches errors, enrichment improves quality" — both halves of that answer sound like the same thing ("makes output better") and read as one role split in two. Say "different aspects of the knowledge gap — correctness for validation, canonicalisation for enrichment." Distinct axes is the whole defence.

8 · The fifth honest-middle binary

"Validation never blocks; enrichment never invents" is one binary. But the slide-13 scope defence — "active, not exhaustive" — is the fifth entry in the deck's contribution-defence series. Every contribution slide names the dismissive reading and refuses it with a precise positive claim.

10 · Four pre-loaded interrupts

"Only 150 armed groups? ACLED has thousands of actor entries. Isn't that a serious coverage gap?"
"ACLED's full actor list includes splinter factions, dissolved groups, and inactive historical entries — many with no recent operations. The 150 in the KB covers the active landscape across the continent. Including inactive groups would actively produce false-positive enrichments — surface forms collapsing to canonical entries that no longer correspond to acting organisations. Mean alias count per group is four-point-two, which is what matters for canonicalisation quality. Recommendation two in section 7.4 specifies a part-time domain expert keeps the KB current as the operational landscape changes."
Four moves: (1) name the right reading of ACLED's list (mixed live + historical); (2) reframe "small" as "active"; (3) name the depth metric (4.2 aliases) that the panel didn't think to ask about; (4) cite the future-work recommendation. Never say "we ran out of time" — that gives the floor away. The scope defence is principled, not apologetic.
"Why both validation and enrichment? Isn't this just a lookup table doing one job?"
"No — they answer different questions about the extracted record. Validation answers is this geographically plausible — a correctness question about the world. The KB provides a country-of-operation fact the model cannot acquire from text. Enrichment answers is this surface variant the same entity as another mention — a canonicalisation question about identity. The KB provides an alias table the model cannot acquire from text. One resource, two distinct knowledge gaps closed. The operational evidence is on slide 19 — the 2.4 % flag rate matters to analysts because they re-read; the 64.3 % enrichment rate matters because aggregate analytics stop double-counting."
Two-axes framing for the KB. Never say "validation catches errors and enrichment improves quality" — that reads as two phrasings of "makes output better." Name the question each role answers — plausibility vs identity — that is the load-bearing distinction.
"What happens if the model extracts an actor not in your KB — a brand-new armed group?"
"The record still persists with the raw surface form. The canonical actor id field is empty; everything else — the location, the casualties, the timestamp — remains. No fabrication. New armed groups not yet in the KB are exactly this case, and they are the largest part of the thirty-five-point-seven percent of ACTOR mentions that don't enrich. The analyst sees the raw text and can flag the new group for KB curation. The enrichment is opt-in by match; absence of a match is silent, not fabricated."
The critical move: keep "no fabrication" front and centre. The CS-panel concern is that the KB might silently invent canonical ids for unmatched mentions — explicitly refusing that closes the failure mode. Naming the 35.7 % unmatched fraction shows that the unmatched case is the design's known and accepted behaviour, not an oversight.
"How do you keep the KB current? Armed-group landscapes change quickly."
"Recommendation two in section seven-point-four addresses exactly this — a part-time domain expert maintaining the KB on a quarterly cadence. The architecture supports this: the KB is loaded from JSON at server startup, so adding aliases or new groups is a configuration change, not a code change. The thesis claim is not that the KB is permanently complete — the claim is that the curated active landscape is the right starting state, and that ongoing curation is part of the operational model. The platform makes the curation cycle cheap."
Three moves: (1) cite the recommendation by section number, signalling this was foreseen; (2) name the architectural property (config-driven KB) that makes curation cheap; (3) reframe the question — the KB is not claimed to be complete-forever, it is claimed to be the right operational shape. Don't get drawn into "how often exactly?" — quarterly is the default; the architecture supports faster if needed.

11 · The hero close

The hero line — memorise verbatim "Validation never blocks extraction; enrichment never invents data."

Why this line is the hero

  • Two negative guarantees in one breath. Negative guarantees are stronger than positive promises for a curated component — they tell the panel what the failure modes cannot be. "Never blocks" closes the gatekeeping failure mode; "never invents" closes the fabrication failure mode.
  • Parallel structure. Same shape — "X never Y" — twice. Parallel structure is what makes pairs memorable. The panel hears it once and can repeat it.
  • Refuses the implicit attack. The implicit CS-panel attack is "you've put a hand-curated component into the pipeline; what could go wrong?" The hero line names both candidate things-that-could-go-wrong and rules them out by design. The attack is neutralised before it is asked.
  • Consistent with the deck's posture. Slide 9: measurement, not preference. Slide 10: decomposed, not narrower. Slide 11: synthesis, not relabelling. Slide 12: complementary, not redundant. Slide 13: metadata, not veto; mapping, not fabrication. Every contribution slide carries its own honest-middle binary; slide 13 carries two in one line.

13 · Quiz

Q1. The panel asks: "Why only 150 armed groups when ACLED has thousands?"

Pick the strongest response.

  • "150 was the largest set we could curate manually within the thesis timeframe."
  • "ACLED's actor list is too noisy to use directly; we filtered to a smaller working set."
  • "ACLED's full list includes splinter, dissolved, and inactive historical entries. 150 covers the active landscape across the continent. Including inactive groups would produce false-positive enrichments. Mean alias count per group is 4.2, which is what matters for canonicalisation. Recommendation 2 in §7.4 specifies ongoing curation by a part-time domain expert."
  • "150 is enough for the most important armed groups — extending it is future work."

Q2. What does the "Validation never blocks extraction" guarantee mean operationally?

Pick the correct meaning.

  • The KB never raises validation flags — every extraction is persisted unmarked.
  • When validation flags a record (~2.4 %), the flag is attached as metadata but the record is still persisted; the UI displays the flag and the analyst decides whether to act on it. The KB does not gatekeep the extraction pipeline.
  • Validation runs after extraction is committed, so it cannot block — it only audits the database retroactively.
  • Records that fail validation are routed to a separate quarantine table for manual review.

Q3. The panel asks: "Why both validation and enrichment from the same KB?"

Pick the strongest response.

  • "Validation catches errors and enrichment improves quality — both make the output better."
  • "Using one curated resource for two jobs is more efficient than maintaining two separate lookup tables."
  • "Validation is for the analyst; enrichment is for the analytics dashboard. Different consumers, same data."
  • "They answer different questions about the extracted record. Validation answers is this geographically plausible — a correctness question. Enrichment answers is this surface variant the same entity as X — a canonicalisation question. The KB closes two distinct knowledge gaps the model alone cannot. Operational impact is on slide 19."

Q4. What happens to ACTOR mentions in the ~35.7 % that don't match a KB entry?

Pick the correct behaviour.

  • The record is dropped — without a canonical actor id, downstream analytics cannot aggregate it.
  • The KB invents a placeholder canonical id from the surface form; the analyst can rename it later.
  • The record persists with the raw surface form in the actor field; the canonical id field is empty. No fabrication — new armed groups not yet curated land exactly here. The analyst sees the raw text and can flag the group for KB curation.
  • The mention is routed to a fuzzy-matching fallback that picks the nearest canonical entry by string similarity.
