1 · Where this slide sits in the arc

Slides 10–13 built the four research contributions: schema, taxonomy + corpus, training recipe, KB. Slide 14 is the fifth contribution — the deployable platform. It is structurally the most exposed slide in the deck because every line on it looks like routine web engineering. That is the point. The slide's job is to convert the apparent weakness — "this all looks like a normal stack" — into the strength: nobody in the academic literature has built this stack for African violent-event extraction and evaluated it end-to-end with users.

The function of slide 14. Two jobs. (1) Own the "isn't this just engineering?" attack inside the slide itself — say it before the panel can. Pre-empting an attack with your own framing of it is how you take the floor away from the dismissive reading. (2) Plant the integration is the contribution claim that slide 22 will close on. The five-contribution close depends on slide 14 having already established that an integrated and end-to-end-evaluated system is itself a research artefact in this domain.

3 · The "engineering pragmatism vs research contribution" distinction

Slide 14's central craft skill is the engineering-as-contribution defence. It is a different defence shape from slides 12 and 13. There, you defended technique combinations (complementarity). Here, you defend a systems artefact by distinguishing what can be swapped without changing the contribution from what cannot.

The swap test — what changes if you swap it?

Swap doesn't change contribution

React → Vue. Different frontend framework, same UI surface.
FastAPI → Flask. Different Python web framework, same routes.
PostgreSQL → MySQL. Different RDBMS, same JSONB storage shape.
Docker Compose → Kubernetes. Different orchestration, same one-command stand-up.

— vs —
Swap WOULD change contribution

Schema → 26 ungrounded labels. Loses the grounding-validated claim.
Loss → plain cross-entropy. Loses the imbalance result.
KB → ungrounded LLM. Loses validation and reproducibility.
UI → notebook. Loses end-to-end UAT evidence.

How to use the swap test under attack. If a panellist questions any individual choice — "why React?", "why FastAPI?", "why Docker Compose?" — answer with the swap test: "swapping it would change implementation, not contribution." Cite the alternative (Vue, Flask, Kubernetes), name the reason for the chosen one (ecosystem, async + PyTorch native, simpler at this scale), and pivot back to the integration claim. The swap test is what stops the panel from drawing you into a stack-religion debate about individual frameworks.

4 · The engineering pragmatism table

For each layer, there is one engineering reason that any working software engineer would accept. None of these are research claims — they are pragmatism. Owning that pragmatism is what makes the integration claim survivable.

Each choice — engineering reason, not research claim

React + TS Largest community + strongest TypeScript ecosystem in 2026. Lowest-risk choice for whoever inherits the system. No research claim being made here.
FastAPI Async-native + first-class PyTorch integration + auto-generated OpenAPI docs. Loading a 110 M-param model into a single worker process is the right shape; Flask + WSGI would lose the async story.
In-process model + KB No network hop between extraction and validation. KB lookup is ~15 % of the 150 ms inference budget because it is in-memory; a remote KB service would push that toward ~50 ms by itself.
PostgreSQL 16 Full-text search + JSONB indexing in one engine. The analytics page needs both — counting events by country (FTS-supported) and querying nested 5W1H fields (JSONB-supported).
Docker Compose One command stands up the whole stack. At 30 k articles/year, a service mesh would be overengineering. Compose hits the deployability target without the complexity tax.

8 · The engineering-as-contribution defence — the core skill

Slide 14's transferable craft is the own-the-attack pre-emption. Most contribution-defence patterns in the deck refuse a dismissive reading by stating a binary contrast ("decomposed, not narrower"). Slide 14's is different — it agrees with the dismissive reading at the surface level ("yes, these are engineering choices") and then names a different level at which the contribution lives ("the integration is the research").

The three-move engineering-as-contribution defence

1Own the engineering framing. Say "defend the stack as engineering, not research claims" yourself. You take the dismissive frame away by stating it first.
2Name the contribution level. "The research contribution is the INTEGRATION evaluated end-to-end." This is the load-bearing move — it names a level at which the contribution exists that is above any individual technology choice.
3Point to the empty cell + the UAT evidence. Slide 6's related-work landscape is the gap; §7.3 contribution #5 is the explicit claim; §6.10 UAT (n=5, six tasks, all completed) is the evidence that the integration was actually evaluated end-to-end.
The trap. Do not get drawn into a stack-religion debate. If a panellist says "I would have used Django/Flask/Vue", do not defend React or FastAPI on their merits — concede the swap ("Vue would work; the research contribution would be unchanged") and pivot back to integration. Defending individual technology choices on their merits cedes the framing: you are then arguing engineering with the panel, not research. The swap test keeps the framing in the right place.

11 · Four pre-loaded interrupts

"Isn't all of this just web engineering? Where's the research?"
"Defend the stack as engineering, not research claims — that's the right reading of the individual choices. React for ecosystem, FastAPI for async plus PyTorch integration, PostgreSQL for FTS plus JSONB. None of those are research claims. The research contribution is the integration evaluated end-to-end. No published academic work in this domain has integrated schema, model, KB, and UI — slide 6's related-work landscape shows that explicitly as an empty cell. Section 7.3 lists this as contribution number five. Section 6.10 is the UAT — five participants, six tasks, all completed. That's the evidence that the integration claim is more than assembly."
Three moves: (1) agree with the engineering framing at the parts level — this is the move most defenders miss; (2) name the contribution level (integration); (3) cite the auditable evidence (slide 6 + §7.3 + §6.10). Owning the engineering framing first is what makes step 2 land — you're not denying engineering, you're naming where the research lives.
"Why monolith and not microservices?"
"At thirty thousand articles a year — the AU-CEWS / ACLED operational scale — a single FastAPI worker holding the 110-million-parameter BERT model in memory is both faster and simpler than a service mesh. The model loads once at startup; every inference is in-process. KB lookup stays at fifteen percent of the hundred-and-fifty-millisecond budget because the KB is in-memory; pulling it into a remote service would push that toward fifty milliseconds by itself. Microservices fit much higher load, where horizontal scaling justifies the network and ops overhead. Not at this scale."
Anchor on 30 k articles/year as the operational load number — that is the scale-justification number. Then connect monolith → in-memory → 15 % latency budget. The latency point closes the architecture decision empirically. Don't argue microservices are bad; argue they are oversized for this load. That is the more defensible framing.
"Why React specifically? I would have built this in Vue / Svelte / vanilla."
"React for ecosystem and TypeScript support — it has the largest community and the strongest TypeScript story in 2026, which is the lowest-risk choice for whoever inherits the system. But the swap test matters here: swapping React for Vue would change implementation, not contribution. The research artefact is the integration evaluated end-to-end — schema + model + KB + UI plus UAT. The UI being React-based versus Vue-based does not change what the integration claim is or whether the UAT validates it. The engineering choice is pragmatism; the research is integration."
The swap test is the whole answer. Do not defend React on its merits — name the engineering reason, deploy the swap test, pivot to integration. If you defend React you are now arguing frameworks with the panel; if you swap-test you are arguing methodology. The methodology framing is the one that wins.
"How do you know the platform is actually usable by analysts? F1 numbers don't tell us that."
"F1 numbers do not — UAT does. Section six-point-ten of the thesis documents the user-acceptance test. Five participants: two early-warning analysts who are the primary intended audience, one academic conflict researcher who is a secondary consumer, and two NLP developers unfamiliar with the conflict domain — that pairing is the fairness sanity check, would someone with technical literacy but no domain knowledge find the interface intuitive. All five participants completed all six end-to-end tasks: paste an article and get chips out; browse persisted events with filters; view per-country analytics; kick off a retraining run from the UI; add a new armed group to the KB; export an event record. The Likert scores are documented in Table 6.10. Slide 19 will deepen the operational impact."
UAT is the integration claim's empirical receipt. Naming the five participants by role (analyst / academic / developer) shows the sampling was deliberate, not "whoever was available." Naming all six tasks demonstrates the platform's surface coverage. Reserve the Likert numbers and the operational-impact reading for slide 19 — on slide 14 you cite the table by name and stop.

12 · The hero close

The hero line — memorise verbatim "The research contribution is the integration evaluated end-to-end. Swapping React for Vue would change implementation, not contribution."

Why this line is the hero

  • Two halves doing two jobs. The first sentence states the positive claim (integration is the contribution). The second sentence makes the engineering-vs-research distinction concrete with a specific swap. Together they answer the canonical attack inside one breath.
  • "Integration" is the load-bearing word. Same syntactic role as "complementarity" on slide 12 and "two roles, one resource" on slide 13. The candidate's contribution-defence vocabulary across slides 12–14 is now: complementarity, two roles, integration. These are the three structural claims that justify the system being more than the sum of its parts.
  • The specific swap is the auditable test. Naming React → Vue is a concrete example the panel can mentally run. Generic statements ("our contribution is the integration") sound like deflection; the specific swap demonstrates the candidate has thought through what the contribution actually depends on.
  • Consistent with the deck's posture. Slide 9: measurement, not preference. Slide 10: decomposed, not narrower. Slide 11: synthesis, not relabelling. Slide 12: complementary, not redundant. Slide 13: active, not exhaustive. Slide 14: engineering pragmatism, research integration. The dismissive reading is named (engineering) and refused (integration) in the same line.

14 · Quiz

Q1. The panel asks: "Isn't this just web engineering? Where is the research contribution?"

Pick the strongest response.

  • "Building this stack required substantial systems engineering — async PyTorch integration, JSONB schema design, and Docker orchestration are all non-trivial."
  • "The trained model is the research contribution; the platform is how we deliver it to users."
  • "Defend the stack as engineering, not research claims — that's right for the individual choices. The research contribution is the integration evaluated end-to-end. No published academic work has integrated schema + model + KB + UI in this domain — slide 6 shows the empty cell. §7.3 lists this as contribution #5; §6.10 is the UAT evidence (n=5, six tasks, all completed)."
  • "React, FastAPI, and PostgreSQL are research-grade choices that justify the academic novelty of the platform."

Q2. What is the "swap test" doing in the slide-14 defence?

Pick the cleanest explanation.

  • It validates that the chosen frameworks are interchangeable, proving the implementation is generic.
  • It separates implementation-level choices (where swaps are admissible) from contribution-level claims (where swaps would invalidate the research). Saying "swapping React for Vue changes implementation, not contribution" names exactly what level the contribution lives at — above any individual technology choice.
  • It is a benchmarking exercise comparing React vs Vue and FastAPI vs Flask on standard metrics.
  • It signals to the panel that the candidate considered multiple alternatives before settling on the chosen stack.

Q3. The panel asks: "Why monolith and not microservices?"

Pick the strongest response.

  • "Microservices are overengineered for academic projects — a monolith is faster to develop and easier to deploy."
  • "Microservices would require a service mesh, container orchestration, and inter-service auth — too much complexity for a thesis."
  • "A monolith is what the FastAPI documentation recommends for ML inference workloads."
  • "At ~30 000 articles per year, a single FastAPI worker holding the 110 M-parameter model in memory is faster and simpler than a service mesh. KB lookup stays at ~15 % of the 150 ms latency budget because the KB is in-memory; remoting it would push that toward 50 ms by itself. Microservices fit much higher load, not this scale."

Q4. The panel asks: "Why React specifically? I would have used Vue."

Pick the strongest response.

  • "React for ecosystem and TypeScript support — lowest-risk for whoever inherits the system. But the swap test matters: swapping React for Vue would change implementation, not contribution. The research artefact is the integration evaluated end-to-end; the UI being React vs Vue doesn't change what the integration claim is or whether UAT validates it."

  • "Vue would have been a reasonable choice; React was preferred because the candidate had prior experience with it."
